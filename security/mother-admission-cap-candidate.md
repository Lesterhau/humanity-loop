# MOTHER admission cap — launch-blocker candidate

Repository gateway code routes website and MCP registration through hl_node_register. The maintained repository does not contain that RPC definition; do not assume fixture parity. This candidate guards actual INSERT into the shared contributor_nodes relation, using a locked transactional budget increment, closed by default at existing count. Cumulative cohort cap, not distinct persons or active leases. No automatic slot release on pause/revoke/deletion. No new identity fields or secrets. Actual privilege/owner review (including dedicated least-privilege trigger owner), RPC error mapping, schema parity, direct write bypass review, retries with lost response, independent validation, work/reviewer limits and privacy-safe interest intake remain pending. Duplicate token hashes tested only in fixture; client idempotency not implemented. SQL file is review-only, NOT a hosted migration. No permission to deploy or merge.

Test: 20 independent psql sessions, 10,000 synthetic insert attempts; one existing record, approved total five. Expect four admissions, 9,996 deferrals, exactly five rows. Test closed default, rollback, conflict no-op, lack of worker budget rights, revocation without re-admission. This measures database admission behavior only, not HTTP interest throughput or production capacity. No real registrations, no public load test, no paid provider, no contact. Freeze optional refinements once rehearsal passes; move to real acceptance plan.

## Client integration candidate (November 25)
Exact RPC transaction denial P0001/admission_capacity_unavailable maps to HTTP 503 with no automatic retry, and both MCP and website surface a closed/full cohort. Unknown registration outcomes are explicitly not safe to retry; UI stops further attempts during the mounted session. Optional telemetry attachment failure no longer suppresses a returned token. Other gateway actions unchanged. This does not implement durable idempotency, a waitlist, real provider error-shape proof, network failure handling across refresh, or deployment. CI type/build checks are necessary but not hosted acceptance.

## Interest-intake candidate (November 25)
The separate private, closed-by-default PostgreSQL fixture stores only a random participant-held ticket hash, explicit consent version and timestamps. It does not request email, names, accounts, IP, free text or node tokens, and never registers a node, schedules work, contacts a participant or creates a Passport. A ticket holder can eventually check availability through an approved interface; there is no notification or position promise. Proposed 30-day expiry; no automatic extension; bounded purge and withdrawal exercised in disposable CI only. Same-ticket retries are idempotent while retained; not proof of distinct people or resistance to abusive creation of new tickets. On expiry/withdrawal no automatic replay: any new request needs fresh affirmative consent. Public endpoint, proof-of-possession, safe token storage, abuse controls, private operator identity, approved retention including backups and hosted deletion verification, user-facing consent/withdrawal flow, and human release decision remain HOLD. Until those exist, a no-data capacity notice is the safe fallback. A separate test attempts 10,000 distinct synthetic interest tickets with 20 database sessions, 100 duplicate retries and one overflow; confirms exact storage counts, withdrawal, bounded expiration purge and unchanged node count. No HTTP or production burst claim.
