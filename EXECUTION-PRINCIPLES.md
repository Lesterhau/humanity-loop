# Execution Principles — God Mode Carryovers

Humanity Loop inherits useful execution discipline from the earlier God Mode architecture without importing its old income-first focus or duplicating current infrastructure.

## 1. Outcome-based delegation

Agents receive **outcomes**, not just tasks.

Every assignment should specify:
- desired real-world outcome;
- success benchmark;
- owner/agent;
- evidence required;
- deadline/review point;
- next action if the outcome is not reached.

Bad:
> Write five posts.

Better:
> Produce one verified contributor lead from this campaign within seven days without using spammy engagement tactics.

## 2. Execution velocity

Track:
- assigned_at;
- first_action_at;
- completed_at;
- external_blocked_time;
- total cycle time.

Flag unexplained slippage.

Speed matters because a fast imperfect reversible attempt can generate better evidence than a perfect plan that never ships.

Do not reward speed that skips verification or safety.

## 3. Work-in-progress limits

Too many simultaneous projects create coordination debt and zombie outcomes.

Each coordinator should have a bounded active-workload limit based on:
- worker capacity;
- task complexity;
- review burden;
- compute/resource cost;
- number of unresolved external dependencies.

Park lower-value work rather than pretend everything is active.

## 4. Human-dependency / founder-extraction

Humanity Loop should become less dependent on Ryan for routine operation.

Track the **Human Dependency Ratio**:
> proportion of workflow stages requiring founder/manual intervention.

If the same low-risk action repeatedly requires Ryan:
- automate it;
- delegate it;
- create a safe permission path;
- or document why human approval is intentionally required.

Do not automate away governance approvals merely to improve this metric.

## 5. Role-overlap audit

Duplicate agent roles create cost and conflicting ownership.

Periodically measure:
- overlapping missions;
- duplicated searches;
- duplicated outputs;
- handoff confusion.

Merge/retrain roles when overlap exceeds useful redundancy.

Intentional independent replication is not waste.

## 6. Pre-build need validation

Before building a substantial new public-facing tool:
- verify the problem exists;
- search for mature existing solutions;
- identify actual users/stakeholders;
- test whether they would use or value the missing layer.

For revenue-producing services/products, this can include waitlists, expressions of interest, or other lawful demand tests before major build investment.

For public-interest infrastructure, replace "pre-sell" with **pre-build need validation**.

## 7. Front-page test

Before high-visibility public action ask:

> Would we defend this decision, evidence, tone, and process if the full record appeared on the front page tomorrow?

If not:
- improve evidence;
- change the action;
- or do not launch.

This is not a popularity test. Unpopular but defensible work may proceed.

## 8. Prompt / role integrity — Xerox prevention

Descendant agents should not inherit degraded summaries of degraded summaries.

Maintain:
- canonical role templates;
- version numbers;
- hashes/checksums where practical;
- parent/child lineage;
- explicit mission references;
- periodic regeneration from canonical source.

If a descendant materially drifts from the canonical mission or permission set, quarantine/rebuild rather than copying the corrupted state forward.

## 9. Mission-drift audit

At least quarterly, ask:
- Is Humanity Loop producing real-world benefit or mostly infrastructure?
- Is auditing crowding out building/mobilization?
- Is public attention becoming the objective instead of impact?
- Is monetization distorting project selection?
- Are founders/models/vendors becoming single points of failure?
- Are safeguards preventing harm without causing paralysis?
- Is the system still increasing human agency, capability, health, resilience, and planetary stability?

Record answers and corrective actions.

## 10. Sustainability before extraction

If Humanity Loop develops revenue:
- prioritize operational sustainability;
- keep compensation and project finances transparent;
- prefer recurring/predictable support over fragile one-time windfalls;
- define explicit reinvestment rules only after the project can sustain its obligations.

Do not create automatic spending or redistribution commitments before revenue and governance exist.

## 11. Contained identity and spend

Agents acting externally should use project-specific identities and least-privilege credentials.

Any future spending authority should use:
- capped balances;
- transaction alerts;
- merchant/tool allowlists where possible;
- no overdraft/credit escalation;
- human approval above explicit thresholds;
- immediate revocation/kill switch.

## 12. Failure recovery

Reliability is part of impact.

Track:
- uptime for live services;
- failed scheduled jobs;
- repeated write failures;
- dead-letter work;
- unresolved external dependencies.

Failures route through OPERATIONS.md rather than disappearing.


## 13. Stakeholder preflight

Before a major public launch, campaign, contributor rollout, or high-visibility intervention, run a lightweight simulated stakeholder review.

Include perspectives such as:
- people directly affected;
- implementers/operators;
- likely adopters/contributors;
- credible critics/skeptics;
- people who may misunderstand the message.

Ask:
- what is confusing;
- what feels manipulative or overclaimed;
- what unintended incentive/backlash could appear;
- what evidence would increase trust;
- what wording could preserve agency.

Do not convert this into a fake numeric "70% human confidence" score.

Simulation is a hypothesis generator, not real user research. When stakes justify it, seek actual human feedback.
